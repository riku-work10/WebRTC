# 10 学習記録: プロセスとジョブ制御

[trap_demo.sh](trap_demo.sh)を使い、`&`でバックグラウンド実行 → `kill`でシグナル送信、という一連の流れを実行して確認した。

## `&` でバックグラウンド実行し、`$!` でPIDを掴む

```bash
sleep 30 &
echo $!      # 直前にバックグラウンドで起動したプロセスのPID
jobs         # このシェルが管理しているジョブの一覧
```

実行結果:

```
started background job, PID=65070
[2]  + running    sleep 30
```

`jobs`は「このシェルの子として動いている処理」をジョブ番号(`[2]`)で管理する仕組み。`$!`は「PID(プロセスID、OS全体で一意)」、`jobs`の`[2]`は「ジョブ番号(そのシェルの中だけで一意)」という別のIDである点に注意。`fg %2` / `bg %2`のようにジョブ番号を使って操作できる(未検証)。

## シグナルと `trap`

```bash
trap 'echo "SIGTERM(15) received..."; exit 0' TERM
```

`kill`は「プロセスを強制終了させるコマンド」というより、正確には「シグナルを送るコマンド」。デフォルトの`kill PID`はSIGTERM(15番、行儀よく終了してくれというお願い)を送る。プロセス側は`trap`でSIGTERMを受け取った時の処理(後片付けなど)を自分で書ける。

実行結果:

```
pid=65115 sleeping, send: kill -TERM 65115
SIGTERM(15) received, cleaning up...
wait exit=0                  ← trapの中でexit 0したので正常終了扱いになった
```

比較として、`trap`を設定していない[08](../08-loops/NOTES.md)以前のプロセスに対して同じように`kill`すると、後片付けの余地なくそのまま終了し、`wait`の終了ステータスは`143`(`128+15`、「シグナル15で死んだ」ことを示す慣習的な値)になることを確認した。

## ハマったポイント: バックグラウンド起動とサンドボックスの相互作用

最初`nohup ./trap_demo.sh &`のように**別のBashツール呼び出しで**バックグラウンド起動し、次の呼び出しで`kill`しようとしたところ、プロセスは残り続け、trapも発火しなかった。1回のシェル呼び出し(1回のBashツール実行)の中で`起動 → sleep 1 → kill → wait`まで完結させたところ問題なく動作した。ツール実行環境ではシェル呼び出しごとにセッション/サンドボックスが分かれる可能性があり、別呼び出しをまたいでPIDを操作するのは信頼できない、という実践的な教訓を得た。
